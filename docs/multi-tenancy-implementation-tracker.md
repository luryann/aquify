## 1. Verdict: where we are today

**Aquify is single-tenant with tenant-shaped plumbing.** The ADR chose "single-club deployment for v1, `org_id` on business tables for forward compatibility." That choice is correctly implemented, and the plumbing is a good foundation. It is **not** safe to put a second club on the same deployment today. The gaps below are structural, not polish.

## 2. Target design (decisions to lock first)

Record these as a new ADR (`docs/decisions/2026-11-xx-multi-tenancy.md`) and update `DECISIONS.md` **before** coding. Recommended answers are in bold.

| ID | Decision | Recommendation |
|---|---|---|
| D1 | Isolation model | **Shared database, shared schema, `org_id` on every tenant row, enforced by Postgres RLS as defense in depth** (app-level filtering stays primary). Schema-per-tenant and DB-per-tenant are rejected: migration fan-out and the Go pool model make them costly for a club-sized SaaS. |
| D2 | Canonical tenant key | **`orgs.id UUID`** everywhere. Slug is a separate unique, immutable-by-default public handle. |
| D3 | Identity model | **DECIDED 2026-11-03: one person belongs to exactly one club.** Keep `users.org_id` as the single membership (make it a FK to `orgs`); no `org_memberships` table, no org switcher. Consequence: the same email cannot be registered at two clubs (Keycloak email is unique per realm); document this and return the existing 409. Revisit only if multi-club people become a requirement. |
| D4 | Active-org selection | **Server derives the org from the session, never from the client.** `X-Org-Id` becomes an optional assertion that must equal the session's active org. Org switching is an explicit authenticated call that mints a new session. |
| D5 | Keycloak topology | **DECIDED 2026-11-03: single realm.** With D3 the `org_id` user attribute and token claim stay the membership source; `users.org_id` in the app DB must match it (reject sessions where they differ). Realm-per-org stays deferred. |
| D6 | Tenant resolution for public pages | **Slug and custom domain → org via the `orgs`/`org_domains` tables, server-side.** Remove client-supplied `org_id` from public flows. Slug route `/club/[slug]` already follows this pattern. |
| D7 | Payments | **OPEN (owner unsure; "each club operates independently" implies this).** Recommendation: Stripe Connect, one connected account per org, `org_id` kept in metadata, so money never lands in the platform account. Not started until confirmed; Phase 5.1 is blocked on it. |
| D8 | Email | **Per-org Postmark sender signature or message stream**, with a shared platform token initially and a per-org from-name/reply-to. Per-org suppression lists (already `org_id` scoped). |
| D9 | Cache strategy | **Org-partitioned in-memory state**: load per org lazily, evict idle orgs, and drop global reload locks. |
| D10 | Platform operator role | **Separate `platform_admin` concept outside the org role tree**, MFA-required, fully audited, no ambient data access (support access is time-boxed impersonation, which today is fail-closed and stays so until built). |

## 4. Verification plan (what "done, securely and without bugs" means)

Do not tick the epic complete until all of these hold:

1. **Isolation matrix**: the two-org Postgres harness (0.2) passes for every route in the route matrix (0.3), for every role (admin, coach, parent, swimmer), for read, list, count, create, update, delete, export, search and download paths, including raw-ID guessing of org B's IDs (expect 404, not 403, to avoid existence leaks).
2. **Mutation checks**: removing the app-level `org_id` predicate from a sample of queries makes the harness fail (proving the tests bite), and with RLS on and the predicate removed the harness still passes (proving the backstop works).
3. **Async paths**: jobs, schedulers, webhooks (Stripe, Postmark), the calendar feed token, presigned URLs and the worker run under the right org only; a forged payload `org_id` that does not match the DB row is rejected.
4. **Concurrency**: two orgs hammering the same instance don't block each other and don't share state (race detector, `go test -race`, lock-contention test); two API instances sharing a DB stay consistent per org.
5. **Identity**: a user in two orgs sees only the active org's data; switching clears server and client state; removing a membership revokes live sessions within one request.
6. **Security review**: run `/security-review` on the branch, plus a manual pen-test checklist (IDOR, mass assignment of `org_id`, header spoofing, token replay across orgs, slug enumeration, registration abuse).
7. **Migration rehearsal**: full up/down on a production snapshot, row counts verified before and after, and a timing report for the locks taken.
8. **Load**: a k6 scenario (`tests/`) with N≥20 orgs showing p95 latency and memory within budget.
