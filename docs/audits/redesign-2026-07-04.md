# Aquify Redesign Pass — 2026-07-04

Follow-up to [[ux-ia-audit-2026-07-03]] and [[usability-audit-2026-07-03]]. Those two passes fixed
nav/IA/copy issues; this pass targets the remaining structural complaint — permanent "form on the
left, browsable content on the right" split-screen layouts that don't hold up for a real club
(100+ swimmers, 200-300+ parents) — plus a content bug on the Approvals page.

Scope confirmed by fresh code review: 6 of the 8 named pages really were permanent split-screens
built around "create one record, browse many records." Two were not: Visualization is a stat-tile +
ranked-list dashboard (no split to remove), and Approvals is a single-column card list with a
content problem, not a layout one. Messages is a split-screen with a legitimate inbox rationale
(thread list + conversation), so it was restyled rather than restructured.

## What changed

- **New shared primitives**: `admin/components/ui/Modal.tsx` (didn't exist before — no
  Modal/Dialog component existed anywhere in the app) and adoption of the existing, previously
  unused `admin/components/ui/Table.tsx` across every redesigned page. Every "create new record"
  form moved off a permanent sidebar into an on-demand modal opened from a "+ New …" button; content
  moved into a full-width, sortable, paginated table with a search/filter toolbar above it.
- **Time Standards**: full-width table + New Standard modal, inline Pause/Activate/Delete actions.
- **Best Times**: reframed as a **team-wide leaderboard by default** instead of a mandatory
  single-swimmer selector — fixes a previously-flagged gap ("no way to see who's fastest in an
  event team-wide," the coach's most common question for this page).
- **Announcements**: full-width feed + stat chips in the toolbar + New Announcement modal.
- **Email Campaigns** (`CampaignsPanel`, `SuppressionPanel`): full-width tables + modals; campaign
  row click still opens the existing `/campaigns/[id]` detail page.
- **Data Exports / Data Deletions**: full-width request tables + modals, subtitle copy translated
  from GDPR jargon to the actual trigger ("A parent asked you to download/delete their data — start
  here").
- **Visualization**: light restyle only (stat chips, toolbar-consistent look) plus converted the two
  ranked lists ("Broadest Coverage," "Most Populated Events") into small horizontal bar charts
  instead of plain text rows.
- **Messages** (admin + portal): kept the two-pane inbox shape, restyled to the same visual language,
  added thread search on the admin side. Unread badges, realtime delivery, edit, reactions, and
  attachments are scoped as a separate follow-up phase (backend schema + new infra, not a pure UI
  change).
- **Approvals content fix**: the pending-user card previously showed a raw `ID: {uuid}` line as the
  most prominent secondary text under the user's name — even though the API already returns name,
  requested role, swimmer/club context, and submission date. Fixed by demoting the ID to a small
  "copy" icon button and leading the card with **Name → Pending/role badges → email/submitted date →
  swimmer/club/note context**. No backend change — the display fields already existed.
- **Campaign sender-identity bug**: previously flagged as "note it, don't fix" in the 2026-07-03
  usability pass (`from_name: 'DARE Aquatics'`, `from_email: 'noreply@dareaquatics.org'` hardcoded
  into every new campaign). Fixed properly since the campaigns panel was already being rebuilt: added
  "Email Sender Identity" (name + address) fields to Settings, backed by two new `org_settings`
  columns (`email_sender_name`, `email_sender_address`, migration
  `20260704000100_org_settings_email_sender.sql`), and the campaign composer now defaults from those
  settings instead of the hardcoded third-party values.

## Deliberately not changed in Phase 1
- Visualization and Approvals structural layout (neither was a split-screen problem).
- Messaging features (realtime, unread counts, edit, reactions, attachments, swimmer-side inbox) —
  scoped for Phase 2 since they needed new DB schema and a new SSE/Redis pub-sub layer, not just
  frontend changes.

## Phase 2 — messaging features (same day, follow-up)

Implemented the messaging feature set scoped above. Backend additions live in
`server/internal/app/comms/` (new `realtime.go` broadcaster, extended `service.go`/`repository.go`)
and four new migrations (`20260704000200`–`20260704000500`) for message edits, reactions,
attachments, and per-user read watermarks. New/changed endpoints: `PATCH /messages/{id}`,
`POST/DELETE /messages/{id}/reactions`, `POST /messages/read`, `POST /messages/upload-url`, and
`GET /messages/stream` (SSE).

- **Coach can message a swimmer directly**: the backend already scoped `swimmer`-role access to
  their own household+swimmer thread — the actual gap was a missing swimmer-portal page, added at
  `admin/app/(swimmer)/swim/messages/page.tsx` with a nav entry in `SwimmerNav.tsx`. The thread stays
  shared with the parent (not a private swimmer-only channel), consistent with the platform's locked
  parent-oversight constraint.
- **Realtime**: `GET /api/v1/messages/stream` (SSE) backed by Redis pub/sub
  (`comms.MessageBroadcaster`), consumed via a manual fetch-based reader
  (`admin/lib/useMessageStream.ts`) rather than native `EventSource`, since EventSource can't carry
  the `Authorization`/`X-Org-Id` headers this API requires. Fails closed to `503` with no `REDIS_URL`
  configured — verified via automated test and does not block any other messaging functionality.
- **Unread counts**: a `message_reads` watermark table (one row per thread per user) drives an
  `unread_count` per thread, shown as a badge pill in the admin inbox; opening a thread marks it read.
- **Edit**: sender-only, unrestricted, shows "(edited)"; edit history kept in `message_edits`.
- **Reactions**: fixed 6-emoji set (👍❤️😂🎉😮😢), toggled per user, aggregated with counts.
- **Attachments**: images only (10 MiB cap), mirrors the existing document upload-url → attach
  validation discipline (real MIME/size/existence checks against storage, not client-declared values).

Found and fixed one real bug during manual verification: reactions only updated the UI via the
realtime event, so in any environment without Redis configured (including this one) a new reaction
never appeared until a manual page reload. Fixed by refetching the thread's messages directly after
a successful add/remove call in all three inbox pages, so reactions work correctly with or without
realtime configured.
